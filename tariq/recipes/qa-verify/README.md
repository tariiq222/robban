# qa-verify — acceptance verification without repair

Three steps: source-only analysis of existing acceptance and exact safe command definitions, verification, independent checker. Custom strong `qa-verifier` / `qa-checker` avoid the canonical reviewer-needs-implementer rule. Both readOnlyRetry=false: command steps may have side effects and are not automatically repeated on missing output.

Inputs: nonblank task and canonical absolute POSIX repo. Analysis must extract explicit task/repository acceptance with basis, not invent missing criteria. Missing acceptance returns ended without command execution. Ambiguous, malformed, unsafe or incomplete contract returns completed_with_failures. No unnecessary decision/resume loop: supply missing acceptance in a new task.

Criteria carry unique stable id AND unique trimmed criterion text, nonblank basis, relevant concrete scoped files, proof source/runtime, and exact listed commands. At most30 criteria and40 files. Runtime criteria require existing safe command definitions; source-only criteria may use no commands. Verification/checker results must account for exactly all criteria, with no duplicate/unknown ids. PASS needs actual nonblank evidence, all criterion files inspected, exact source/runtime proof type, and every required command reported once as passed with integer exit0. Checker independently reads/reruns rather than accepting author report. Missing checker, malformed evidence, failed or blocked checks never grant PASS. Author failed/blocked status cannot be erased by checker approval. Any reported failed/blocked authorized command in either verification or checking prevents completed, even when that command is additional to the passing criteria's required commands.

Results contain status completed/completed_with_failures/ended, summary, criteria, results, stage-attributed commands, coverage, changedPaths[], next_actions, limitations and reviewTrail. If the checker is missing, malformed or throws, valid verifier failed/blocked rows retain their evidence, file/command references and verifierStatus/verifierEvidence; checkerStatus is blocked. Author-only PASS remains blocked until independently checked. With a valid checker, final evidence/files/commands come from the failing or blocked stage rather than a contradictory PASS; verifierEvidence and checkerEvidence remain separately available. Source PASS is explicitly not runtime proof. This recipe never implements or repairs.

## Permissions and limits

Analysis private marker readOnly:true is mechanically restricted by updated host to read/read_image/glob/grep/structured_output. Verify/check readOnly:false permits existing safe shell checks: no-edit is PROMPT-ONLY, not shell/read-only enforcement. Before running any command the agent must inspect its definitions and refuse destructive/network installer/credential/unsafe effects as blocked. Exact command accounting is not proof the model actually executed it; independent evidence review is essential. A safe:true source report is a declaration, not a shell-security sandbox. Tests may generate outputs, so verification is not guaranteed zero filesystem side effects despite changedPaths[] meaning no authored repair. No install/restart/commit/deploy/repair authorized. Direct offline execution without routingToken has caller-owned restrictions.
